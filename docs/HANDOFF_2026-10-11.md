## 3. Decisions D1 to D5 (planner's decisions, parent plan section 6)

- **D1 persistence:** SQLite by default, through `BTB_DATABASE_URL` (the `web.database_url` default is `sqlite:///out/btb.db`). External Postgres on Render is the intended production path. **Only SQLite was run.** The Render deployment and persistence were not tested.
- **D2 accounts:** anonymous households with a recovery key. No email or Google login. Deleting a household needs the recovery key.
- **D3 live audio in Full mode:** **not built.** T3.9 is gated on the audio spike (`docs/superpowers/plans/2026-10-10-multi-household/audio-spike.md`). Audio stays off in every mode.
- **D4 video:** JPEG previews over the existing WebSocket. **Not WebRTC.** T5.4 is a spike that was not written.
- **D5 Blackout:** kept as a separate mode from the events-only Privacy mode. The order is `blackout < privacy < limited < full`.

## 4. Not done, or not verified

- **Not built:** live audio (T3.9); T5.3 (optional higher-resolution preview); T5.4 (WebRTC spike); phase 7 (E2EE, audit log). Phase 7 has no task files yet (parent plan section 7).
- **Render:** deployment and persistence are **untested**. The Render free-tier facts (ephemeral disk, spin-down, egress, Postgres lifetime) are **unverified** (parent plan section 1.4).
- **Keystore:** the release build fails loudly without a release keystore (`d5477f2`). PAT and `release.jks` handling was not reviewed or changed in this session.
- **Android Keystore:** the planner's brief says the A07 uses a TEE-backed key, not StrongBox. This session did not verify that.
- **Notifications and approval:** tested on one phone only (the SM-E075F). Notification-approval check 16 passes on that phone.
- **Public PIN:** the PIN was removed from `render.yaml` (`cce571a`) but it **remains in git history**. The owner must **rotate the live Render PIN**; this repo cannot do that.
- **Unexplained listener:** on 2026-10-11 a process was listening on `0.0.0.0:8001` (pid 119681, `python -m uvicorn backend.main:app --host 0.0.0.0 --port 8001`), reachable from the LAN. It was not started by this work, and it was not touched. **The owner decides** whether to stop it.
- **Fixed in this session, and why it mattered:** `DELETE /households/me` removed the directory taken from the owner runtime's config. A station that connects with its own id replaces the idle `default` channel, and that station's config carries the shared `web.log_dir` root. A later delete then removed the whole root. In the default config the root is `out/`, which also holds `out/btb.db`. The existing isolation test `test_delete_removes_one_household_only` missed this because its households never had a station take over the default channel. Fixed in `1143624`, reproduced by `tests/web/test_erasure.py` (fails before the fix, passes after; `f72e9a7`).

## 6. Security summary (what the isolation tests cover)

`tests/web/test_isolation.py` (9 tests) is the gate that every later phase must keep green. It covers:

- no cross-household leak on any surface (`/ws`, `/events`, `/status`, `/video`);
- spoofing a household id changes nothing;
- revoking one station leaves the other household alone;
- deleting one household removes only that household's data;
- non-legacy households never touch the LLM or external notifiers;
- event-log files stay in their household directory;
- pin mode still serves one legacy household;
- a mode change in one household never affects another;
- a two-household, two-station matrix.

`tests/web/test_erasure.py` (1 test, added this session) covers the erasure path that the gate had missed. Pairing uses ECDSA P-256 challenge-response (`web.auth.mode: households`). Pairing codes are one-time and expire after 300 s. The dashboard never shows "Reconnecting" for a deliberate stop, and a viewer is limited to `min(station cap, household mode, viewer ceiling)`.
