## 0. Decisions (made by the planner, owner can overrule)

1. **Audio belongs to Full mode.** Full = live video + live audio. Limited, Privacy and Blackout never carry audio (the phone does not send it and the server refuses to relay it). The dashboard shows a **Listen** button (browsers forbid autoplay): muted by default, one tap starts sound, stays on until stopped or the 180 s inactivity watchdog fires. Viewers whose `mode_ceiling < full` cannot open the audio socket (403).
2. **Codec: IMA-ADPCM by default, PCM16 selectable, Opus reserved.** Raw PCM16 at 16 kHz is 256 kbps (about 2.7 GB per listener per day of egress, which matters on a metered host); IMA-ADPCM is 4 bits/sample = about 64 kbps (about 0.7 GB/day) with no codec dependency, trivial to implement identically in Kotlin and TypeScript and robust to loss because every 100 ms chunk is an independent block. Codec byte in the frame header: `0` PCM16, `1` IMA-ADPCM, `2` Opus (reserved, not implemented).
3. **Mic reuse:** streaming reuses the existing `MicSource` 100 ms chunks (the same `AudioRecord` YAMNet uses); no second recorder.
4. **E2EE scope (honest):** the server never sees plaintext **media** (video previews and audio) in an E2EE household, protecting against a compromised/curious relay, logs, snapshots at rest and TLS-terminating proxies (threat vector 4 in `docs/privacy_architecture_and_threat_model.md`). It does NOT protect against an actively malicious server that serves modified dashboard JavaScript, and it does NOT cover events (emotion, timeline, battery), which the server needs. Keys never touch the server: they travel only in the pairing QR (phone) and in the URL fragment of invite links (viewers). Algorithm: AES-256-GCM (WebCrypto-native), HKDF-SHA256 subkeys. Key rotation in v1 = re-pair (documented); an `epoch` field is reserved.
5. **Isolation:** all work happens in the git worktree; the owner's uncommitted Postgres/R2 storage work in the main checkout is never touched.

## 2. Part A: live audio (T3.9 for real)

Wire format, phone to server (binary WebSocket message on `/ingest-events`):
`0x02 | codec u8 | seq u32 LE | t_ms u32 LE | payload`
- codec 0: 1600 samples s16 LE (3200 bytes). codec 1: block = `predictor s16 LE | step_index u8 | 0x00` followed by 800 bytes (1599 samples as nibbles, low nibble first). Reference IMA step/index tables (the standard 89-entry step table) live in `docs/AUDIO_WIRE.md` with test vectors generated by `scripts/audio_vectors.py`.
Server to viewer: `GET /audio` WebSocket (binary). First text message `{"type":"audio_hello","codec":1,"rate":16000,"chunk_ms":100,"station":"<id>"}`; then each phone frame forwarded verbatim (the `0x02` byte dropped). Per-client bounded deque of 20 frames (2 s), oldest dropped.

## 4. Part C: opt-in end-to-end encrypted media

Design recap (decision 4). A household has `e2ee: bool` (default false; set at creation or switched on later with a clear warning that existing viewers/stations must be re-paired). When true:
- **Key custody.** The 256-bit household key `K_h` is generated in the owner's browser (WebCrypto `getRandomValues`) and stored only in IndexedDB. The pairing QR (v3) carries it to the phone: `{v:3,url,pair_url,code,k:<base64url>}`; the phone wraps it with an AndroidKeyStore AES key (non-exportable) at rest (`KeyVault`). Viewer invite links carry it in the **URL fragment** (`...?join=CODE#k=...`), which browsers never send to servers. The recovery bundle offered at household creation includes `K_h`. The server stores and logs nothing about `K_h`; QR payload generation for e2ee households therefore happens client-side (the server's pairing endpoint returns only `code`/URLs; the dashboard adds `k` locally before drawing the QR).
- **Subkeys.** `K_video = HKDF-SHA256(K_h, salt=station_id, info="btb/v1/video")`, `K_audio` likewise with `"btb/v1/audio"`.
- **Frame.** Phone to server binary: `kind u8 (0x05 video, 0x06 audio) | ver u8 = 1 | epoch u16 BE | mode u8 | session u32 BE | counter u64 BE | ciphertext || tag16`. `mode` is the stream's effective mode (1 privacy..3 full; only Limited/Full media exist) and is authenticated (part of AAD) but readable by the server so it can enforce viewer ceilings without decrypting. Nonce (12 bytes) = `session(4) || counter(8)`; `session` is random per station connection; counter starts at 0 per session and never repeats. AAD = all header bytes before the ciphertext || station_id UTF-8. Video plaintext = the JPEG; audio plaintext = the `codec|seq|t_ms|payload` block from Part A. Viewers reject non-increasing counters per `(station, session, kind)`.
- **Server.** In an e2ee household plaintext media (`0x01`, `0x02`) from stations is rejected and counted (no downgrade); `0x05/0x06` frames are relayed untouched to `GET /media` (WebSocket binary, one socket multiplexing video and audio, each message prefixed with a 1-byte station index and the same frame bytes) to viewers whose ceiling >= the frame's `mode`; the server never decodes them. Server-side features that need pixels are unavailable for e2ee households and the UI says so: Limited-mode blur happens on the **phone** (phone sends blurred low-res frames with `mode=limited`), `/video` serves only a "end-to-end encrypted: use the live player" slate, LLM interpretation and external notification snapshots are disabled, peek is phone-side.
- **Dashboard.** `frontend/lib/e2ee.ts` (WebCrypto), `/media` client: decrypt, draw JPEG to canvas (`createImageBitmap`), feed audio to the Part A player; clear states: "key missing in this browser" (with how to fix), "decrypt failed" (counter), "waiting for station".
- **Tasks.** E0 spec `docs/E2EE_SPEC.md` + vector script `scripts/e2ee_vectors.py` writing `tests/vectors/e2ee_v1.json` (fixed key, station id, session, counters, plaintexts, headers, ciphertexts) as the single source of truth; E1 implementations + vector tests in Python (`backend/web/e2ee.py`, header parsing and test-side decrypt only), TypeScript, Kotlin (`javax.crypto` `AES/GCM/NoPadding`, API 26 ok); E2 key custody (browser IndexedDB, QR v3, Android `KeyVault`, invite fragments, recovery bundle) with tests; E3 phone encrypt path (video + audio, Limited-mode phone-side blur) with the plaintext path unchanged when e2ee is off; E4 backend household flag, `/media` relay, ceilings, no-downgrade, isolation and "server cannot decode" tests (the relay test asserts byte-for-byte forwarding and that no module under `backend/web` imports the AES primitive for media); E5 dashboard `/media` client and UI states, vitest for the pure parts; E6 phone acceptance checks 19 (e2ee pairing with key via the debug extra, frames arrive encrypted, Python test client decrypts and the JPEG/audio decode, plaintext `/video` refused) and 20 (revoked viewer/ceiling, replayed counter rejected); docs.
